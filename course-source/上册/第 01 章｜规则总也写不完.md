## 一个夏天

1956 年 6 月，你坐了很久的车，来到美国新罕布什尔州一个叫汉诺威的小镇。这里有一所大学，达特茅斯学院。会场就在数学系那栋楼的顶层。

你是被一份提案请来的。提案写于前一年的 8 月 31 日，打字机打的，署名四个人：达特茅斯的年轻数学教员 John McCarthy，哈佛的 Marvin Minsky，IBM 的 Nathaniel Rochester，还有贝尔实验室的 Claude Shannon。四个人里，只有 Shannon 当时已经名满天下；发起这件事的 McCarthy，还不到 29 岁。

提案的标题里有一个词，是 McCarthy 为了这次会议新造的：**artificial intelligence**。

这个问题本身并不新。六年前，英国数学家图灵就在一篇论文里问过：机器能思考吗？他嫌这个问法太虚，干脆把它换成了一个可以动手检验的游戏：隔着屏幕用文字聊天，你分得出对面是人还是机器吗？后来人们管这个游戏叫图灵测试。

图灵提出了问题。现在，有人打算动手造了。

你在车上已经把提案读了两遍。第一页有一句话，你用铅笔画了线：

> 学习的每一个方面，或者智能的任何其他特征，原则上都能被描述得足够精确，精确到可以造一台机器来模拟它。

紧接着的一句，你画了两道线。他们说，只要一组精心挑选的科学家在一起干上**一个夏天**，就能在其中一个或几个问题上取得重大进展。

再看他们列出的问题：让机器使用语言。让机器形成抽象和概念。让机器改进自己。

一个夏天。

（顺便说一句：他们向洛克菲勒基金会申请了 13500 美元，基金会批了 7500。经费砍掉将近一半，目标一个字没改。如果你做过项目，此刻应该已经有了不祥的预感。）

![[零基础学AI/attachments/第 01 章｜规则总也写不完/GxSlbwUmJoeJLexJIQCcKjvlnRd.png|1956 年夏天，达特茅斯。一份提案，一块黑板，一个夏天。]]

其实这个夏天，大家来来去去，凑不齐一屋子，很多人只待了几天。但有两位客人带来了一样真东西。Allen Newell 和 Herbert Simon 从匹兹堡赶来，带着一个已经能运转的程序，名字起得毫不谦虚：Logic Theorist，逻辑理论家。

它做的事情是证明数学定理。给它几条公理和几条推理规则，它就自己一步步往下推。后来的测试里，罗素和怀特海那部《数学原理》第二章的前 52 条定理，它证出了 38 条。其中有一条，它找到的证明比书上的还短、还漂亮。据 Simon 后来回忆，他们把这个新证明投给了逻辑学期刊，作者栏里写上了这个程序的名字。期刊退稿了。

请在这里停一下，体会一下 1956 年的心情。

一台机器，按照人写给它的规则，推出了连罗素都没找到的证明。那么，照这个思路往下走：语言有语法规则，下棋有棋规，看病有诊断规则。把规则一条条写清楚，交给机器，剩下的不就是时间问题吗？

提案里其实还列着另一条路，叫“神经元网络”：不写规则，让机器看例子，自己摸索。可那样的机器该怎么造，1956 年没人说得清。眼前这条路，已经有程序在跑了。

现在，假设有人递给你一个题目：**让机器接住人说的一句话。** 你走哪条路？

在心里选一条再往下读。不用写下来，但要真的选。

我猜你选了写规则。当年几乎所有人都这么选，而且他们有很好的理由。这条路后来有了一个名字，叫**符号主义**：把知识写成机器能摆弄的符号和规则。这一章，我们就陪着这个选择往下走，看它能走多远。

## 回到你的键盘前

1956 年的程序员用的是打孔卡片，写一个 Logic Theorist 要先发明一门编程语言。为了不把这本书变成考古学教材，我们把场景搬回你的电脑前，只从 1956 年带走一样东西：那个信念。**把规则写清楚，机器就能照办。**

我们的题目也换成你身边的事。部门来了新同事，总有人问同样的问题。你想做一个小小的问答入口，先把问题分个类：这句话是在问**账号申请**，还是在问**软件安装**？

规则好像很明显：

```python
# router.py：资料助手 v0.1
def reply(text):
    if "账号" in text:
        return "账号申请"
    if "安装" in text:
        return "软件安装"
    return "未识别"

if __name__ == "__main__":
    print(reply("账号怎么申请？"))
    print(reply("软件怎么安装？"))
```

（需要 Python 3.9 或更高版本，不用装任何库。本章所有代码都是这样。）

运行它：

```
账号申请
软件安装
```

两句都接住了。六行代码，一个能用的程序。说实话，这种感觉挺好的，1956 年的人就是被这种感觉鼓舞的。

可是，这两句话是你自己想的，规则也是照着它们写的。它当然答得对。要知道它到底行不行，得拿它没见过的话来问。

我替你准备了六句，写在另一个文件里。前两句就是刚才那两句，后四句是别人会怎么问：

```python
# exam.py：拿一份没见过的考卷，考一考任何一版 reply
exam = [
    ("账号怎么申请？", "账号申请"),
    ("软件怎么安装？", "软件安装"),
    ("登录用的身份怎么办理？", "账号申请"),
    ("开发环境部署失败了", "软件安装"),
    ("账号已有了，软件怎么安装？", "软件安装"),
    ("软件已经安装好了，账号怎么申请？", "账号申请"),
]

def run(reply, questions=exam):
    right = 0
    for text, want in questions:
        got = reply(text)
        right += got == want
        print("✓" if got == want else "✗", text, "->", got)
    print(f"{right}/{len(questions)}")

if __name__ == "__main__":
    from router import reply
    run(reply)
```

运行之前，先猜一下：六句里它能对几句？哪几句会错？

真的猜一下。把数字记在心里。

```
✓ 账号怎么申请？ -> 账号申请
✓ 软件怎么安装？ -> 软件安装
✗ 登录用的身份怎么办理？ -> 未识别
✗ 开发环境部署失败了 -> 未识别
✗ 账号已有了，软件怎么安装？ -> 账号申请
✓ 软件已经安装好了，账号怎么申请？ -> 账号申请
3/6
```

对了一半。和你猜的一样吗？

错的三句，值得一句一句看。

“登录用的身份怎么办理？”说的明明是账号，可句子里没有“账号”这两个字。“开发环境部署失败了”也是一样，没有“安装”。**同一个意思，人有一百种说法。** 我们的规则只认得其中一种。

第五句更有意思。“账号已有了，软件怎么安装？”两个关键词都在。可程序读到“账号”就交卷了，后半句它根本没看。

再看第六句，“软件已经安装好了，账号怎么申请？”它答对了。你觉得它是真看懂了吗？

把 `reply` 里两个 `if` 的顺序对调，再跑一次，你就知道了：第六句会错，第五句会对。它答对第六句，只是因为“账号”这条规则碰巧排在前面。

这是全书第一个要记住的教训，后面每一章都用得上：**答对了，不等于弄懂了。** 只看分数，你分不清这两件事。

## 那就再补一条

你现在肯定手痒了。问题这么明显，补一条规则不就行了？

好，我们补。先解决第五句：两个词都出现的时候，回答安装。

```python
# patch1.py：第一个补丁，两个词都出现时，回答安装
from exam import run

def reply(text):
    if "账号" in text and "安装" in text:
        return "软件安装"
    if "账号" in text:
        return "账号申请"
    if "安装" in text:
        return "软件安装"
    return "未识别"

run(reply)
```

猜猜现在几分？

```
✓ 账号怎么申请？ -> 账号申请
✓ 软件怎么安装？ -> 软件安装
✗ 登录用的身份怎么办理？ -> 未识别
✗ 开发环境部署失败了 -> 未识别
✓ 账号已有了，软件怎么安装？ -> 软件安装
✗ 软件已经安装好了，账号怎么申请？ -> 软件安装
3/6
```

还是 3 分。第五句对了，第六句错了。按下葫芦浮起瓢。

![[零基础学AI/attachments/第 01 章｜规则总也写不完/FLmub6EwUozpcPxwr8ccAZDinLe.png|补上一个，又冒出一个。]]

想想也是：第五句和第六句长得一模一样，都是“某某已经办好了，某某怎么办”。区别只在于，哪件事是**已经办完的**。程序得能分清这个。

那就再补：如果句子里说账号“已经有了”，就不算在问账号；说软件“已经安装”了，就不算在问安装。

```python
# patch2.py：第二个补丁，已经办完的事不算数
import re
from exam import run

def reply(text):
    need_account = "账号" in text and not re.search("已经?有账号|账号已", text)
    need_install = "安装" in text and not re.search("已经?安装|安装好", text)
    if need_account and need_install:
        return "软件安装"
    if need_account:
        return "账号申请"
    if need_install:
        return "软件安装"
    return "未识别"

run(reply)

print("—— 隔壁同事探头进来，随口问了两句 ——")
run(reply, [
    ("账号还没开通，安装也做不了", "账号申请"),
    ("账号已过期，怎么重新申请？", "账号申请"),
])
```

代码开始不好看了，那两行正则表达式，你自己过一个月也未必看得懂。跑一下：

```
✓ 账号怎么申请？ -> 账号申请
✓ 软件怎么安装？ -> 软件安装
✗ 登录用的身份怎么办理？ -> 未识别
✗ 开发环境部署失败了 -> 未识别
✓ 账号已有了，软件怎么安装？ -> 软件安装
✓ 软件已经安装好了，账号怎么申请？ -> 账号申请
4/6
—— 隔壁同事探头进来，随口问了两句 ——
✗ 账号还没开通，安装也做不了 -> 软件安装
✗ 账号已过期，怎么重新申请？ -> 未识别
0/2
```

第五、六句都对了，4 分。

可输出里还有后半段。就在你准备庆祝的时候，隔壁同事探头进来，随口问了两句。

“账号还没开通，安装也做不了。”这位同事需要的是账号。程序看到两个关键词，都不属于“已经办完”，于是套上第一个补丁：回答安装。错。

“账号已过期，怎么重新申请？”程序看到“账号已”三个字，认定账号的事已经办完了，于是什么都没认出来。错。我们为了接住“账号已有了”写下的那条规则，把“账号已过期”也一起吞了。

把这三轮的成绩放在一起看：

![[零基础学AI/attachments/第 01 章｜规则总也写不完/XPlzbQF5UorQNlxaoTFcjYqvn6g.png|补了两轮，换来了什么：同一份考卷，三个版本的 reply。]]

这张表里藏着三件事。我建议你盯着它看半分钟，试着自己说出来，再往下读。

第一件：`reply` 从 6 行长到了 10 行，见过的题只多对了一道。

第二件：没见过的题，一道没对。**补丁是照着考卷改的，所以它只对考卷有效。** 那六句话被我们反复看、反复改，早就不是“没见过的题”了。拿它们的分数来证明程序变好了，就像学生自己出题、自己答、自己打满分。

第三件最要命：每一条新规则，都可能和旧规则打架。“两个词都有就答安装”和“已经办完的不算”，各自单看都有道理，合在一起就要多想好几种情况。我们现在只有四五条规则，已经得很小心了。五十条呢？

你也许会想：这是因为我写得太糙。换个聪明人，认真设计，多写一些，总能写周全吧？

1960 年代的研究者也这么想。其中有一位，把这条路走得特别漂亮。

## 一个让人想倾诉的程序

1966 年，麻省理工学院。你坐在一台电传打字机前，机器连着楼里那台大型计算机。有人告诉你，里面有个程序，可以和它聊聊。

你试着敲了几句。下面这段对话出自作者后来发表的论文，我把它译成了中文。左边是一位年轻女士敲的字，右边是程序的回答：

| 人 | 程序 |
|-|-|
| 男人都一个样。 | 怎么个一样法？ |
| 他们总为这为那地烦我们。 | 你能举个具体的例子吗？ |
| 嗯，是我男朋友让我来这儿的。 | 你男朋友让你来这儿的。 |
| 他说我大部分时间都很消沉。 | 听说你很消沉，我很难过。 |

这个程序叫 ELIZA，作者是 MIT 的 Joseph Weizenbaum。名字取自萧伯纳的戏《卖花女》里那位学说上流话的姑娘。它扮演的是一位心理咨询师。

先别往下看。想一个问题：要写出一个能这样接话的程序，得让它懂多少东西？它需要知道“男朋友”是什么吗？需要知道消沉是一种不好的感觉吗？

答案是：都不需要。

再读一遍右边那一列。“你男朋友让你来这儿的。”不过是把对方的话换了个人称还回去。“你能举个具体的例子吗？”放在任何一句抱怨后面都成立。只有最后一句像是懂了点什么，可它其实是一条写死的规则：看到“消沉”这类词，就说“我很难过”。

ELIZA 的全部本事是三步：在句子里找到一个认识的模式，把句子拆开；把“我”换成“你”；把拆出来的后半句套进一个事先写好的模板。

![[零基础学AI/attachments/第 01 章｜规则总也写不完/NZ8db8wLDocaXdxtFzOcgOj2nd3.png|ELIZA 的把戏：拆开、换人称、套模板。三步都只碰字面，不碰意思。]]

我们自己写一个。二十几行就够：

```python
# eliza.py：分解 → 换人称 → 重组
import re

SWAP = str.maketrans({"我": "你", "你": "我"})

script = [
    (r"我担心(.+)", "你为什么担心{0}？"),
    (r"我觉得(.+)", "是什么让你觉得{0}？"),
    (r".*(妈妈|爸爸|家里).*", "多说说你的家人吧。"),
]

def eliza(text):
    text = text.rstrip("。！？")
    for pattern, template in script:
        m = re.fullmatch(pattern, text)
        if m:
            parts = [g.translate(SWAP) for g in m.groups()]
            return template.format(*parts)
    return "请继续说。"

for line in [
    "我担心入职后跟不上。",
    "我担心你不理解我。",
    "我觉得流程太复杂了。",
    "我妈妈也这么说。",
    "让我不踏实的是入职后跟不上。",
    "我担心的不是入职，是房租。",
]:
    print(line, "->", eliza(line))
```

脚本里只有三条规则。猜一猜，下面六句话里，哪几句它能接得像模像样？

```
我担心入职后跟不上。 -> 你为什么担心入职后跟不上？
我担心你不理解我。 -> 你为什么担心我不理解你？
我觉得流程太复杂了。 -> 是什么让你觉得流程太复杂了？
我妈妈也这么说。 -> 多说说你的家人吧。
让我不踏实的是入职后跟不上。 -> 请继续说。
我担心的不是入职，是房租。 -> 你为什么担心的不是入职，是房租？
```

前四句接得相当不错。第二句连“你不理解我”都翻成了“我不理解你”，乍一看简直通人情。

第五句换了个说法，脚本里没有“让我不踏实的是”这个模式，它只好说一句万能的“请继续说”。真正的 ELIZA 在这里更狡猾一点：它会翻出你之前说过的某句话，来一句“这和你男朋友让你来这儿有关系吗”，让你觉得它一直在认真听。

第六句最能说明问题。模式对上了，它高高兴兴地拼出一句：“你为什么担心的不是入职，是房租？”

**它不知道自己说了什么。**

现在你可以自己玩一会儿：往脚本里加规则，看看要加到多少条，才能让它不闹这种笑话。别玩太久，这是个无底洞，而且后面还有更重要的事。

### 然后，奇怪的事情发生了

按理说，这么一个小把戏，谁也骗不了。Weizenbaum 自己也是这么想的。在他眼里，这只是一个研究人机对话的小实验。

结果正相反。

他后来在书里写到一件事。他的秘书看着他写这个程序，前后好几个月，比谁都清楚那只是一段代码。有一天她坐下来和 ELIZA 聊了几句，然后转过头，请他离开房间。

她想和它单独谈谈。

![[零基础学AI/attachments/第 01 章｜规则总也写不完/PpBEbBbwCoGpOVxyaQ9cgRgunIh.png|她比谁都清楚那只是一段程序。她还是请他出去了。]]

还不止这一件。有精神科医生读了论文，认真地提议：这样的程序稍加完善，就可以用来给病人做治疗，一台计算机一小时能接待好几百人。

Weizenbaum 被吓到了。他没想到，和一个这么简单的程序聊上几句，就能让完全正常的人产生这么深的错觉。此后的许多年，这位 ELIZA 的作者成了对 AI 最不留情面的批评者之一。

这件事，请你带着走完这本书：

> 💡
>
> **程序让人觉得“它懂我”，这是一回事。程序里面是怎么算出那句话的，是另一回事。** 前者看聊天记录就能知道，后者得打开盖子才能知道。六十年后的今天，我们面对的程序比 ELIZA 复杂得多，这句话照样成立。

下次有个程序让你觉得它真懂你，你打算怎么检验？先别急着回答。你在上一节其实已经用过一个办法了：拿它没见过的话去问它。

## 给资料助手造第一块零件：活字字模箱

再把时间往回拨十二年。1954 年 1 月 7 日，纽约，IBM 总部。

在 ELIZA 让人对着打字机倾诉之前，人们最想让计算机干的语言活儿，其实是翻译。那天下午，乔治城大学的语言学家和 IBM 的工程师当着记者的面，往一台 IBM 701 计算机里塞进了几十句俄语——有化学的，也有政治的。

机器咔哒咔哒地吐出英文：“加工提高了煤的质量。”“淀粉由机械方法生产。”

第二天，《纽约时报》的标题乐观得像刚过完节。按 IBM 当年的新闻稿，主持实验的学者预计：五年，也许三年以后，几种语言在一些重要实用领域里的电子翻译，可能成为现实。他同时提醒，把一本俄文书塞进去、另一头直接出来一本英文书，当时还做不到。

先别看后来的事。假如你那天就站在机器旁边，有机会掀开盖子看一眼，你会发现它的全部家当只有两样东西：**一本只装了 250 个俄语词的词典，和 6 条语法规则。**

计算机不认得俄语字母，也不认得汉字。它只认得数。你可以把它想成老式印刷厂的**活字字模箱**：排字师傅手里只有一盒刻好的常用字模，每个字模底下标着一个编号。一句话递过来，机器先照着这本小词典把句子拆成一块一块，再把每一块换成字模箱里的编号；接着，那 6 条规则上来，按编号排顺序、挑词义。

![[零基础学AI/上册/attachments/Pasted image 20261117121815.png]]

那 60 多句俄语，全是从这 250 个词里精挑细选出来的。可要是换一份未经挑选的俄文报纸，遇到这份小词表没有收进的词，原来的查表办法就接不住了。演示成功，不等于任意文章都能翻。1966 年，美国政府请委员会评估各家机器翻译的实效，交上来的报告冷冰冰的：又慢，又贵，还不如请人翻。那句“五年，也许三年”，后来走了半个多世纪。

不过，1954 年那台机器干的**第一步**——拿一只字模箱，把一句话切成小块，换成编号——却一直留到了今天。

还记得导论里说过吗？整本上册，我们要从零亲手造出一个**资料助手**。前面六行 `router.py` 只能硬匹配关键词，离真正自己开口说话还差得远。从今天起，每一章我们都替它打一块新零件。

今天先打第一块零件 `cut.py`：一只只装了 8 个常用词的迷你字模箱。凡是箱子里找不到的字，就拿一块空白木头顶上去，一律记成 `0`（意思是“眼生，不认识”）。拿它去切我们那张六句话的考卷：

```python
# cut.py：资料助手的第一块“识字”零件。拿一本小词典，把一句话切成块、换成编号
from exam import exam

vocab = {
    "<unk>": 0, "账号": 1, "软件": 2, "怎么": 3,
    "申请": 4, "安装": 5, "已经": 6, "有了": 7, "好了": 8,
}

def cut(text):
    out, i = [], 0
    while i < len(text):
        if text[i] in "？，。":
            i += 1
        elif text[i:i+2] in vocab:
            out.append(vocab[text[i:i+2]])
            i += 2
        else:
            out.append(0)
            i += 1
    return out

if __name__ == "__main__":
    for text, _ in exam:
        print(f"{text} -> {cut(text)}")
```

运行之前，先盯着考卷上的第三句和第四句看一眼：它们变成字模编号以后，会是什么样？

```
账号怎么申请？ -> [1, 3, 4]
软件怎么安装？ -> [2, 3, 5]
登录用的身份怎么办理？ -> [0, 0, 0, 0, 0, 0, 3, 0, 0]
开发环境部署失败了 -> [0, 0, 0, 0, 0, 0, 0, 0, 0]
账号已有了，软件怎么安装？ -> [1, 0, 7, 2, 3, 5]
软件已经安装好了，账号怎么申请？ -> [2, 6, 5, 8, 1, 3, 4]
```

看第四句，“开发环境部署失败了”：清一色的九个 `0`。

在程序眼里，这九块空白木头和“今天中午吃什么呀”是一模一样的，反正全是不认识的字。第五句也很妙，“账号已有了”里的“已”字单独出现，字模箱里只有两字的“已经”，没有单字的“已”，于是它被一刀切成了 `[1, 0, 7]`，中间硬生生漏掉了一截意思。

你大概已经看出来了：在写任何规则、做任何训练之前，**你先拿什么刀去切这句话，就已经决定了机器能看见什么、看不见什么。** 字模箱里缺了的字、切坏了的词，后面再聪明的大脑也救不回来。

这件只有二十行的小工具，请你存进第 01 章的文件夹里。到第 04 章，它会正式上岗，帮资料助手迈出“自己开口接话”的第一步。

## 把专家装进机器

回头看，ELIZA 之所以能撑住场面，靠的是避重就轻。它从不回答问题，只负责把话还给你。心理咨询恰好容得下这种谈话方式，所以 Weizenbaum 选了这个角色。

可我们的问答入口不能这样。新同事问“我该走哪个入口开通账号”，你不能回他一句“你为什么想知道该走哪个入口”。

它得真的知道点什么。

那就把知识也写进去。把懂行的人请来，把他知道的东西一条一条问出来，写成“如果……那么……”，交给机器。这个想法在 1970 年代成了气候，有了一个响亮的名字：**专家系统**。

早期最有名的一个出自斯坦福，叫 MYCIN。它帮医生判断血液感染是哪种细菌引起的、该用什么抗生素。它的知识库里是几百条这样的规则（意译）：

> 如果　病原体的革兰氏染色是阴性，并且形态是杆状，并且是厌氧菌，  
> 那么　有相当的把握（0.6）认为它是拟杆菌。

写规则的是医生，套规则的是程序。程序还能解释自己：你问它为什么这么判断，它就把用到的规则一条条列给你看。在一次蒙住名字的评比里，几位专家给各家的治疗方案打分，MYCIN 的得分不比参评的斯坦福医生低。

你可能要问：这么好，后来怎么没在医院里见到它？

它从来没有真正用在病人身上。原因有很多，其中一条特别实在：出了错算谁的。这个问题，我们到第 14 章还会碰到，到今天也没有完全解决。

### 1980 年，一个真正上了岗的

真正让专家系统红起来的，是一桩生意。

想象你是 1980 年数字设备公司（DEC）的工程师。公司卖的 VAX 计算机不是整机，客户订的是一堆部件：处理器、内存、磁盘、机柜、线缆。哪些部件能搭在一起、缺了什么、线怎么接，全靠技术人员一单一单地配。配错是家常便饭，货发到客户那里才发现少一根线。

卡内基梅隆大学的 John McDermott 替 DEC 写了一个专家系统，后来叫 XCON。它把配置的门道写成规则，自动检查每一张订单。它真的管用。据估计，它每年给公司省下几千万美元。

消息传开，企业纷纷成立 AI 部门。专门用来跑这类程序的计算机，Lisp 机器，卖得很好。1956 年那个夏天没兑现的东西，看上去终于要兑现了。

我们也来做一个，体会一下它的味道。假设公司开账号的规矩是这样的：新入职的同事需要账号；需要账号并且经理批准了，就走标准入口；实习生走独立入口（因为要导师和部门双签）。

```python
# expert.py：事实 + 规则 → 推理出结论
rules = [
    ({"新同事"}, "需要账号"),
    ({"需要账号", "经理已批准"}, "走标准入口开通"),
    ({"实习生"}, "走独立入口开通"),
]

def infer(facts):
    facts = set(facts)
    changed = True
    while changed:              # 一直推，直到推不出新东西
        changed = False
        for need, then in rules:
            if need <= facts and then not in facts:
                facts.add(then)
                changed = True
    return sorted(f for f in facts if f.endswith("开通"))

print(infer({"新同事", "经理已批准"}))
print(infer({"新同事", "实习生", "经理已批准"}))
```

`rules` 是知识库，`infer` 是推理机：拿着眼前的事实，把规则一条条套上去，套出新的事实就记下来，直到再也套不出新东西。

这个结构有一个很大的好处，值得你停下来欣赏一下：**知识和程序分开了。** 规矩变了，只改 `rules`，不动 `infer`。上一节的路由器可做不到这一点，它的规则是和 `if` 搅在一起的。

现在来两位新同事。第一位是普通正式新员工，经理批准了。第二位是**来实习的**新同事，经理也批准了。先猜：程序会让第二位走哪个入口？

```
['走标准入口开通']
['走标准入口开通', '走独立入口开通']
```

两个入口，它都推出来了。

三条规则，每一条单独看都没毛病，都是懂行的人亲口说的。合在一起，遇到一个“既是新同事又是实习生”的人，它们就打起来了。

你来修。动手之前先想清楚，你打算怎么修。

我猜你想到的是这两种办法里的一种。要么改第二条规则，加一个条件：“需要账号，经理已批准，**并且不是实习生**”。要么加一条新规则：“两个入口都推出来的时候，听独立入口的”。

两种都能修好。但请注意你刚才做了什么。第一种办法，你让一条规则开始操心另一条规则的事。第二种办法，你写了一条**关于规则的规则**。

规则多了以后，这类事情没完没了。

![[零基础学AI/attachments/第 01 章｜规则总也写不完/HDpSb0wGxokmpVxF2KHcnOSYnYc.png|规则是点，要操心的是线。规则翻一倍，线大约翻两番。]]

XCON 上岗时不到一千条规则，后来长到了上万条。DEC 不得不养着一支专门的队伍，天天改规则。产品一更新，就有一批规则要改；改完一条，还得确认没有碰坏别的。

![[零基础学AI/attachments/第 01 章｜规则总也写不完/LahjbXWQLoCvObxNlsxcMFnLnVb.png|把专家装进机器：知识库装经验，推理机负责套用。难的是左上角那两支虚线箭头。]]

### 说不出来的那部分

规则打架，还只是麻烦之一。更深的一个麻烦，藏在图上那两支虚线箭头里：把老师傅脑子里的东西**问出来**。

做个小实验。请你用“如果……那么……”写下规则，教一个从没用过聊天软件的人判断：同事发来的这条消息，急不急？

你大概会写：有“尽快”“马上”就是急。有三个感叹号就是急。领导发的就是急。

然后你自己就会想到例外。有的人每句话都带感叹号。有的人越急越客气，只发一句“在吗”。你的直属领导半夜发来一个“？”，比一百个感叹号都急。

你明明一眼就能看出一条消息急不急。可要你把“怎么看出来的”写下来，你写不全。

1966 年，就是 ELIZA 发表的那一年，哲学家 Michael Polanyi 把这件事说成了一句话：**我们知道的，比我们说得出来的多。**

做专家系统的人给它起了个行内的名字，叫“知识获取瓶颈”。专家当然懂，可专家说不清自己是怎么懂的。说出来的那一部分，往往只是最规整、最像教科书的那一部分。

剩下说不出来的那部分里，有一大块我们平时管它叫**常识**。研究者 Douglas Lenat 喜欢讲一个例子：有一个诊断皮肤病的专家系统，你把一辆生了锈的旧车的情况输进去，它会一本正经地告诉你，这辆车得了麻疹。

它没有任何一条规则写着“车不会得麻疹”。谁会想到要写这个呢？

## 冬天

1984 年，美国人工智能协会的年会上，有两位研究者公开提醒同行：企业界对 AI 的期望已经吹得太高，失望是迟早的事。其中一位我们认识，就是当年在达特茅斯提案上签名的 Marvin Minsky。他们给即将到来的东西起了个名字：**AI 寒冬**。

三年以后，冬天来了。1987 年，Lisp 机器的市场垮掉了：普通的工作站和个人电脑越来越快、越来越便宜，没有人再愿意为专用机器付高价。与此同时，许多公司发现，自家那套专家系统越养越贵，当初说好的效果却没有来。钱和热情一起退了潮。

![[零基础学AI/attachments/第 01 章｜规则总也写不完/UHa5bmsMXoVptPx0ctOc4oyZnLS.png|两次乐观，两次退潮：1950—1987。曲线只画期望的起落，不代表任何实测数据。]]

图上还有一个更早的低谷，在 1970 年代。那一次受伤最重的，是你在达特茅斯没有选的那条路。那是下一章的故事。

这个冬天里，有一个人的选择特别值得一提。1984 年，也就是“寒冬”这个词出现的同一年，Douglas Lenat，就是讲麻疹故事的那位，启动了一个项目，叫 Cyc。他的想法很直接：既然机器缺的是常识，那就把常识写给它。一条一条，用手写。“水是湿的。”“人死了就不会再活过来。”“车不会得麻疹。”

他当时估计，这件事需要很多人干上很多年。

他说对了。这个项目做了几十年，写下的条目数以百万计。2023 年 Lenat 去世的时候，它还没有写完。

![[零基础学AI/attachments/第 01 章｜规则总也写不完/RDlcb77lToxs1Dxy50dcrm4dnng.png|一条一条，用手写。]]

这一章的标题，说的就是这件事。

## 那么，你当年选对了吗

回到 1956 年那个下午，你在心里选的那条路。

选了写规则的你，选中了之后二十多年的主流，亲手做出了能证明定理的程序、让人想倾诉的程序、每年省下几千万美元的程序。这条路是真的走通过的。

它撞上的墙，你这一章也亲手摸过了三次：同一个意思有无数种说法，规则只认得你想到的那几种；规则一多就互相打架，照看它们的功夫涨得比规则本身还快；而最要紧的那些知识，懂的人自己也说不出来。

三堵墙后面是同一件事：**我们想让机器处理的东西，大部分写不成规则。**

这不是说规则没用了。请记住它真正擅长的地方，本书后半部分会反复回到这里：凡是**必须说一不二**的事，都应该写成规则，交给普通的程序去执行。“没有经理批准，不得开通账号”这种事，不能让任何聪明的模型去“判断”，它就该是一行 `if`。聪明的部分交给会学的东西，不许出错的部分交给规则。这个分工，到 2026 年也没有变。

还有一件事，你可能已经自己联想到了。今天很多人给 AI 写提示词，写着写着就成了这样：“如果用户问到价格，就……；如果用户语气不好，就……；但如果同时问到价格而且语气不好，则……”一个例外补一条，补到几千字。

1980 年代的知识工程师要是看到，会觉得非常亲切。

## 这一章你留下了什么

三个文件，请存好，它们会陪你走完这本书。

`router.py`，是我们资料助手的第一个版本，**v0.1**。请留意，我们留下的是最初那个六行的版本，不是打过补丁的。原因你已经知道了：补丁是照着考卷改的。一个老老实实的 3 分，比一个掺了水的 4 分更适合拿来当起点。往后每一章的新办法，都要回来和它比一比。

`exam.py`，是那张六句话的考卷。从现在起请遵守一条纪律：**不许再照着它改程序。** 它是用来考试的。

`cut.py`，是资料助手的第一块“识字”零件——那只迷你活字字模箱。眼下它只是把句子切成一串编号，第 04 章它会正式派上用场。

到本书结尾，资料助手会长成 v2.0：自己能学着接话、能查资料、能动手做事、隔天还接得上话。它将来不管多能干，都是从这几行开始的。
