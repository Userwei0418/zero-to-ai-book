## 为什么“调完试了一句觉得挺好”是工程大忌？

上册第 01 章定过全书第一条纪律：**考卷是用来考试的，不许照着考卷打补丁。** 上册第 13 章又展示过：凭感觉挑一两个例子看效果，最容易制造“已经修好了”的假象。

在知识库和 RAG 开发里，这种假象天天都在发生：

- 你发现问“一刀切在了除外前面”时，某一段没排进第 1 名；
- 于是你大笔一挥，把 `ingest.py` 的切块长度从 500 字改成了 180 字，或者把 `search.py` 里标题命中的加权系数从 `1.5` 调到了 `5.0`；
- 你重新问了一遍“一刀切”，排第 1 了！你高高兴兴提交了代码，却根本不知道原来稳稳排第 1 的“感知机楼梯灯”和“AlphaGo 第 37 手”已经被你这一改挤出了前三名。

没有一份固定的自动化回归考卷，你每一次“优化”，都可能是在拆东墙补西墙。

```json
  },
  {

    "expected_file": "第 12 章｜多请几个助手，事情就会更顺吗？.md"
  }
]
```

拿这张考卷去考 `search.py` 时，我们不看模糊的“感觉”，只算两个硬指标：

1. **`Hit@3`（前三召回率）**：检索返回的前 3 个文本块里，有没有包含 `expected_file`？有就得 1 分，没有得 0 分。如果连前 3 都没进去，后面的大模型再聪明也是巧妇难为无米之炊。
2. **`MRR`（Mean Reciprocal Rank，平均倒数排名）**：光进前 3 还不够，排第 1 和排第 3 的含金量不一样。如果正确答案排第 1，得 `1/1 = 1.0` 分；排第 2，得 `1/2 = 0.5` 分；排第 3，得 `1/3 ≈ 0.333` 分；没进前 3 得 `0` 分。全卷平均下来就是 `MRR`——它极其敏感地反映了你的排序质量有没有退化。

## 完整回归评测实现：`eval.py`

```python
# eval.py：第 11 章实战成品——自动化回归评测（Hit@3 召回率 + MRR 平均倒数排名）
# 用法：python3 eval.py
import json
import os
import sys

sys.path.insert(0, os.path.abspath(os.path.join(os.path.dirname(__file__), "../ch04")))
import search

EVAL_PATH = os.path.join(os.path.dirname(__file__), "eval_set.json")


def run_eval():
    cases = json.load(open(EVAL_PATH, encoding="utf-8"))
    docs = search.load_chunks()
    hit3, mrr_sum = 0, 0.0

    for c in cases:
        hits, modes = search.hybrid_search(c["question"], docs=docs, top_k=3)
        sources = [h["source"] for h in hits]
        rank = next((i + 1 for i, s in enumerate(sources) if c["expected_file"] in s), 0)
        if rank > 0:
            hit3 += 1
            mrr_sum += 1.0 / rank
        mark = "✓" if rank > 0 else "✗"
        print(f"{mark} [{c['id']}] rank={rank or '-'} | 期望={c['expected_file']} | 实际Top1={sources[0] if sources else '无'}")

    n = len(cases)
    print(f"\n回归评测汇总：Hit@3 = {hit3}/{n} ({hit3 / n:.1%}), MRR = {mrr_sum / n:.3f}, 通道 = {modes}")


if __name__ == "__main__":
    run_eval()
```

请你盯着第 3 行 `[Q3]` 看十秒钟：

`Hit@3` 虽然是满分 `6/6 (100.0%)`，但 `MRR` 只有 `0.889`，因为问 `Q3`（“1966 年的 ELIZA 是靠哪三步把戏让人产生它懂我的错觉的？”）时，实际排在 Top 1 的居然是《写在最后.md》，而真正的《第 01 章｜规则总也写不完.md》排在了第 3 名！

为什么？因为我们在《写在最后.md》里刚好写了一句总结：“觉得 1958 年的感知机、1966 年的 ELIZA、1986 年的四页论文……”，那一段字数短，“1966 年的 ELIZA”词频密度极高，纯字面启发式精排就把它顶到了第 1 名。

你看，**如果没有这张考卷和 `MRR` 指标，只看 `Hit@3 = 100%` 你根本发现不了这个细节。** 有了这张基准表，接下来不论你是接入商汤 **Token Plan** 的 `/embeddings` 和 `/rerank` 模型，还是调整第 03 章的切块大小，只需要花 0.5 秒跑一遍 `eval.py`，看一眼 `MRR` 是从 `0.889` 涨到了 `1.000`，还是跌到了 `0.750`，高下立判。

> “每次改代码前先锁死一组基准测试（Benchmark），改动后自动重跑对比指标”，这就是软件工程里的**持续集成与回归测试（CI & Regression Testing）**。在 AI 工程里，你的 `eval_set.json` 就是防止系统越改越退化的压舱石。
