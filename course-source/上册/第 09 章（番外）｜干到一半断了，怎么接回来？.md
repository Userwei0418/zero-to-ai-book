# 第 09 章（番外）｜干到一半断了，怎么接回来？

配套课件在这里：[[零基础学AI/attachments/mygpt-companion-20261117-r4-8c90a8fb.zip|下载上册配套代码与实验材料（r4）]]。解压后先读 README，按对应章节说明使用。

上一章我们把圈转起来了。可只要圈转得够长，早晚会撞上一件不好看的事：**干到一半，断了。**

清单已经写进新电脑，屏幕却停在“正在保存”。你等了一会儿，没有下一句话。重新打开助手，上一次对话还在，最后一条记录写着：准备写入 `day1.md`。

现在怎么办？

让它再来一次，最省事。可你刚才已经打开那份清单，在末尾添了一句新决定。如果它把原来的内容再写一遍，你那句话就没了。不重来，也有另一种可能：它其实只写了一半，文件名在，后半篇不在。

第 09 章问的是“下一步由谁决定”。这一篇补上另一半：**决定已经作了，动作也开始了，程序断了再重开时，谁来说明它究竟做到了哪儿？**

## 把时钟拨回 1992 年的一间机房

先别急着写提示词。这个问题，做数据库的人三十多年前就撞过。

1992 年的一间机房里，程序刚更新一条记录，机器突然断电。重启以后，有些变化落在磁盘上，有些还只在内存里。你不能看见“程序没有正常结束”，就认定所有事情都没发生；也不能看见一部分新数据，就认定整件事完成了。

你会在哪儿留一笔记录？动手之前，还是做完之后？

只在做完之后记，恰好可能来不及；只在动手之前记，又只能证明“打算做”。所以两边都要有：**先留下意图，完成后再留下结果，恢复时查清中间的空白。** 1992 年发表的经典论文 ARIES 讨论的正是这套基于预写日志（Write-Ahead Logging）的恢复思路。

到了 2025 年 11 月，Anthropic 复盘长时间运行的编程 Agent 时，发现了一模一样的坑：哪怕有了循环和上下文压缩，只要中间断过一次，下一次会话接班时要么留下做了一半的烂摊子，要么过早宣布已经完成。他们给出的办法也是同一条老路：**留下进度文件与状态记录，让接班的会话先核对现场，再继续干活。**

## 一张卡片，两笔流水账

给每一次会留下痕迹的动作（比如把资料助手的清单写进 `result.md`），在动手之前先建一张小卡片：

- **操作编号**：例如 `handover:checklist:r3`（沿用同一次动作，不能偷偷换掉）；
- **目标位置**：`workspace/result.md`；
- **打算写什么**：这次准备写入的完整内容及其**字节指纹（hash）**。

接着在流水账里留两笔：

1. `intent`：准备把这份内容写到这个位置；
2. `done`：写入完成并读回核对后，记下结果。

![[零基础学AI/上册/attachments/Pasted image 20261117032651.png]]

而且每一笔都要立刻刷进硬盘（`flush` + `fsync`），不能等程序正常退出时再写。如果最后一行只有 `intent` 没有 `done`，你就立刻知道：**它正准备做，还不知道做没做成。** 这正是我们在第 08 章留下的第三种状态——结果未知，需要核对。

## 六种中断现场，怎么接？

真把子进程杀在写入前后，对比“不管三七二十一直接重写”和“先查 `intent` 再核对现场”两种恢复策略，差别清清楚楚：

| 中断现场 | 直接重写会怎样 | 先查现场再恢复怎么处理 |
| :--- | :--- | :--- |
| **写完，完成记录没留下** | 又写一次，表面内容相同（若换成发通知就是发两遍） | 读回文件字节指纹一致 → 补记 `done`，**不再重写** |
| **只记了 `intent`，还没写入** | 能补写，但说不清为何缺失 | 确认旧进程已退出且目标不存在 → 补完这次创建 |
| **写到一半截断了** | 直接覆盖残片，现场消失 | 文件存在但指纹不一致 → **停下保留现场**（注意：要按字节而非 UTF-8 文本核对，截在半个汉字上也会报错） |
| **断线后你手动改过内容** | 你的新决定被旧内容盖掉 | 指纹不一致 → **保留你的修改**，停下等你确认 |
| **已有 `done`，后来文件被删** | 可能把你故意删的文件又建回来 | 报告“完成后缺失”，**不自动重建** |
| **旧操作编号带了新正文** | 分不清是重试还是新请求 | 拒绝沿用旧编号，报告请求冲突 |

还要留意一条细缝：**光有一个操作编号，还不等于“幂等”。** 幂等说的是同一次请求重试时不会产生第二份副作用；编号只是让接收方认出“这是不是同一次”的线索。本地写文件靠稳定路径、固定内容和按字节回读就能接上；换成发邮件、扣款等外部服务，就得依赖对方服务真正支持的幂等键或状态查询接口。

## 你按了停止，它真的停了吗？

还有一种“断”，不是断电，是你自己按了停止按钮。

想象子进程已经走到写入前，你发出了取消请求。此刻去看硬盘：文件还没有，可子进程还没退出。这时候你敢在界面上写“已取消，什么都没做”吗？

不能。如果在途的写入线程没有理会取消信号，一秒后文件还是会落盘。

**“用户不想继续”“程序不再派新动作”“已经发出去的动作确实停下了”，是三件不同的事。** 收到停止请求时，最稳的做法是立刻停止派发新动作；对已经在途的动作，能撤回就等撤回确认，不能确认就诚实标记为“结果未知”，随后再回头核对现场。

## 真实工具里也要核对两样东西

哪怕没有断电，把这些接进真实的终端助手（比如开源的 Pi 编程助手），现场记录依然能帮你抓出隐蔽的 bug。在参考课件的一次实测里，写入工具写完文件后向模型汇报“写入 `627 bytes`”，模型也老老实实照着汇报“627 字节”；可独立用程序按字节读回硬盘文件，实际大小是 `1,489` 字节——原来工具源码把中文字符串的字符长度（`content.length`）直接标成了 `bytes`。

![[零基础学AI/上册/attachments/Pasted image 20261117032812.png]]

所以，任何时候查看一条 Agent 的运行记录，都要把三样东西分开读：
1. **模型提出的 `tool_calls`**：是它“打算做什么”；
2. **工具返回的结果**：是工具自称“发生了什么”；
3. **独立读回磁盘/系统的状态**：才是世界“实际变成什么样”的最终证据。

## 这一篇你留下了什么

把第 09 章的循环和这一篇的恢复合在一起，你的 **Harness** 才算真正扛得住长任务：动手前认清操作编号并写下 `intent`，断线重开时按外部事实核对指纹，收到取消信号时分清请求与在途结果。

下一次我们回到第 09 章结尾留下的那个问题：**工具和做法都做稳了，换一个助手、换一个同事来用，难道要重新接十二根线吗？** 这就是第 10 章要讲的 MCP、Skills 与 Hook。
