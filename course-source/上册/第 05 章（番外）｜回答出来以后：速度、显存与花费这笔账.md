# 第 05 章（番外）｜回答出来以后：速度、显存与花费这笔账

配套课件在这里：[[零基础学AI/attachments/mygpt-companion-20261117-r4-8c90a8fb.zip|下载上册配套代码与实验材料（r4）]]。解压后先读 README，按对应章节说明使用。

上一章我们刚刚拆穿了“多轮对话”的秘密：每聊一轮，应用都要把从头到尾整摞消息重新发给模型。于是，当你的资料助手真的跑起来、甚至同时有几个同学一起用的时候，麻烦马上就来了——页面转圈转半天、花钱变多、本地电脑甚至直接爆显存。

模型暂时不换，这一篇我们专门把**速度、显存、并发和花费**这笔工程账摊开算清楚。

## 先递来第一页，还是等整本印完：流式返回

![[零基础学AI/上册/attachments/Pasted image 20261117024407.png]]

手边有两个按钮：一个是等模型把整篇回答全部写完再一次交给你（非流式）；另一个是写出一小段就先显示一小段（**流式返回**，Streaming）。

这就像寄信：先拿到第一张纸，人可以先读，不用干盯着空白屏幕；但**最后一张纸并不会因为先寄了第一页而提前写完**。而且如果第一张纸上只写了“好的，我来想想”，也不等于已经拿到了能用的正文。

## 预算压得太小，会怎样？

看见等待变长，一个很自然的念头是：我只要两句话，干脆把请求里的输出上限 `max_tokens` 压小，比如改成 `16`。

真这么干，常常会撞上一个极其隐蔽的坑：网络请求返回了成功（HTTP 200），耗时也只有 1 秒，**可正文是空的！**

![[零基础学AI/上册/attachments/Pasted image 20261117024514.png]]

为什么？翻开返回的信封看一眼 `usage` 就明白了：

```json
{
  "prompt_tokens": 211,
  "completion_tokens": 358,
  "completion_tokens_details": {"reasoning_tokens": 307},
  "total_tokens": 569
}
```

对于带“思考过程”的模型，它动笔写可见正文之前，会先在草稿纸上琢磨一阵——这部分消耗单列在 `reasoning_tokens` 里（注意：它是 `completion_tokens` 的**细分项**，算总输出时千万别把 307 再加一遍）。如果 `max_tokens` 只给了 16，模型刚在草稿纸上写了 16 个思考 token，额度耗尽直接被截断（`finish_reason` 为 `"length"`），根本还没轮到吐出可见正文。

所以收货程序不能只看“请求有没有报错”，至少要分清三件事：**正常结束（`stop`）、预算截断（`length`）、中途断线**，再检查正文是不是空的。

## 显存为什么越聊越挤：KV Cache 与分页

多个人同时来问，或者一场对话聊到几十轮，哪怕模型权重本身放得下，机器显存也常常会爆。

回想第 04 章的注意力计算：每新生成一个词，都要回头去算前面所有词的 Key 和 Value。为了不每走一步都把前面几千个字重新算一遍，推理引擎会把算过的 K 和 V 暂存在显存里，这叫 **KV Cache**。

模型权重就像机器已经学会的本事，大小固定；**KV Cache 则跟着你的对话长度和并发人数一起膨胀**。如果每个请求一进来就提前划走一大块连续显存、最后没用完又白白浪费，很快就会出现内存碎片。2023 年提出的 **PagedAttention（vLLM）**，正是从操作系统的**分页内存管理**借来的老办法——把 KV Cache 切成小块散着放，逻辑上连着、物理上不用非得挨着，把空洞都利用起来。

## 并发、前缀缓存与“少塞废话”

面对四件互不依赖的小事（比如同时检查四份文档的状态），串行一个一个问要等 `9.61 秒`，开两个并发同时问只要 `5.39 秒`——**整批等待时间缩短了，但四个问题消耗的总 token 一点没少**。并发只省时间，不省钱；而且如果第二步必须依赖第一步的结果，就不能图快一起丢出去。

另外，很多平台支持**前缀缓存**（例如多次请求前面垫着同一长段系统说明和背景材料时，服务可以跳过前面重复部分的计算，主要节省读入阶段的时间，生成阶段照样要一个字一个字吐）。但记住：**不要为了等缓存命中，把无关的旧档案长期塞进每一个问题里**——先去掉这次不需要的材料，永远是最稳的降本增效。

## 如果想放进自己电脑：算一道量化账

不想老调云端接口，想把开源权重下载到自己电脑或实验室服务器上跑，先拿纸算一道账。

假设一个 70 亿参数（7B）的模型，每个数按 16 位浮点数（2 字节）存，光权重就要占 **14 GB**；如果做 **4 位量化**（把精度压粗到每个数半字节），权重体积缩小四倍，变成 **3.5 GB**。

那么，一台只有 4 GB 可用显存的电脑就一定能跑得动吗？**跑不动。** 因为权重大小只是下限——刚才讲的 KV Cache 还没算，计算时的临时工作区、量化所需的缩放比例表也还没算。更何况，位数压粗以后必然带来数值误差（好比把 `0.79` 四舍五入存成有限刻度再还原成 `0.8571`），所以“4 位够不够用”还得拿你自己的考题测质量。

## 留一本版本账本

最后送给工程实践一条救命习惯：当某天你发现昨天还能过关的资料助手今天突然胡说八道，不要只记一句“用的是 `sensenova-6.8-flash`”。

把**资料的哈希值、模型名、接口地址、`max_tokens` 和 `temperature` 参数、原始响应和结束原因**统一记进一本版本账本。只有把“材料变了、模型版本变了、还是运行预算变了”分开记，出了问题你才知道该去查哪一项。
